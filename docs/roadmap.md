# QuantumView ロードマップ

最終目的は、ChromiumやOS標準WebViewに依存せず、HTML/CSSのローカルUIをアプリへ組み込める、小さなWebView代替ホストを作ること。メモアプリは描画・日本語入力・ホスト連携を実証する最初のサンプルであり、プロジェクトの最終成果物ではない。

まず、日本語を入力し、自動保存し、再起動すると続きを書ける単一メモを完成させる。その実装で必要だったホスト処理だけを切り出し、メモ以外の最小画面でも利用できることを確かめる。この順序で進める。

## 現在地

- Servo 0.7.0、Dioxus Native 0.7.10、WebView2比較版のreleaseビルドと起動は成功。
- 3本の実行ファイルをSHA-256で固定し、各3回のアイドル測定を実施済み。
- 予備値ではServoのメモリ関連指標はBlitzより小さい。Servoは表示・変換・取消・Ctrl+C/Vをユーザーが確認済み。連続入力時にフォーカスを失う経路を最小修正し、修正版の実機確認待ち。Blitzとの描画・操作の同等性も未確定で、採用は未決定。
- 画面取得ツールに障害がある。ツールの復旧や検証専用プロジェクトのビルドを、アプリ開発の前提にしない。

## 進める順番

| 段階 | やること | 終了条件 |
| --- | --- | --- |
| 1. 操作を確かめる | 固定済みのServoから、描画、日本語IME、編集、クリップボード、スクロール、リサイズを確認。Blitzも同じ項目で確認し、WebView2を基準にする | 必須項目を合格・不合格・未確認で記録し、どの構成でメモ用途が成立するか分かる |
| 2. 性能と採用を決める | 操作が成立した構成で未測定の起動時間・スクロール時CPU/GPU/メモリを測る。条件が変わっていなければ既存のアイドル値は再利用 | 日本語操作を満たし、リソース使用量と制約を説明できる構成を1つ選ぶ |
| 3. メモを完成させる | 採用構成だけに、単一メモの編集、自動保存、起動時の復元、保存状態・失敗の表示を追加 | 日本語・複数行・絵文字を編集し、終了直前の変更を含めて再起動後に復元できる |
| 4. 配布して使う | exeと必要なUI・リソースを一式にまとめ、ソースツリーの場所に依存せず起動できるようにする | 別フォルダーへ展開し、ビルドせず起動・編集・保存・再起動復元できる。ここをメモアプリv0の完了とする |
| 5. WebView代替ホストとして切り出す | メモで使った描画・入力・ホスト連携を、アプリ固有の状態・保存から分離する | 同じホストをメモと別の最小HTML/CSS画面から利用できる。APIは実際に使った操作だけに限定する |

段階1・2では、Servoを先に検証する順番と、最終的な採用の決定を分ける。採用判断にはWebView代替としての制約も含める。Blitz/Dioxus NativeはRustでUIロジックを書く構成なので、HTML/JS資産の流用や一般的なWebViewとの互換性が成立したとは扱わない。どちらの候補も必須操作を満たさない場合は、問題と必要な修正規模を整理して方針を見直す。

## 次の作業：段階1

1. 固定済みバイナリーの起動手順を整理する。Servo/Blitzは追加コンソールを作らずに起動する。
2. Servoで初期画面、日本語の欠け、文字数、クリア、末尾カードまでのスクロール、狭い幅での1列表示を確認する。
3. 「にほんご」→「日本語」の変換・確定・取消、候補位置、キー編集を確認する。
4. メモ帳との間で日本語・複数行・絵文字のコピー・貼り付け・切り取りを確認する。
5. Blitzでも同じ確認を行い、WebView2と結果を並べる。自動操作で確認できない項目は、ユーザーの実機操作で記録する。

既存の[操作確認手順](https://github.com/watanuki-azuma/QuantumView/blob/main/docs/comparison.md)を使い、同じチェックリストを別に作らない。確認のたびにコードを変えたり、計測をやり直したりしない。

## ビルドと測定の進め方

- 既存の3本と比較用HTML/CSS/JSは基準として保持する。比較画面を変更せず、メモ画面は採用構成にだけ追加する。
- 機能確認は既存バイナリーで始める。実機で確認した不具合の修正や、採用後の機能実装で必要になった場合だけビルドする。
- 関連する変更をまとめ、既存のCargoプロジェクト・target・ロックファイル・同じツールチェーンを使う。検証用の別Cargoプロジェクトや依存更新は追加しない。
- 修正版は別のリビジョンとして記録し、元の固定バイナリーや測定値へ混ぜない。再測定は変更の影響がある項目に絞る。
- 起動時間はウィンドウ生成時刻で代用せず、内容が描画されるまでを確認する。ウォーム起動とOS再起動後のコールド起動は分ける。
- ビルドと性能測定を同時に走らせず、待機中の同じ状態確認で対話を繰り返さない。

## メモアプリで必要になる設計だけを入れる

- 保存先はアプリ用のUTF-8ファイル1つ。自動保存では入力のたびの不要な書き込みを避け、終了時に未保存の変更を残さない。保存失敗を利用者が分かるようにする。
- Servoを採用した場合は、メモの読込・保存に必要な最小のJS–Rust通信だけを実装する。BlitzならRustから直接呼ぶ。複数エンジン共通の通信層は作らない。
- 配布用のリソース読込は、ソースツリーを離れて起動するために必要な範囲だけ変更する。
- 比較用UIを残すのは、同じ描画量で再測定できるようにするため。将来の画面遷移や複数画面対応のためではない。

段階5の別画面は、ホストがメモ固有のコードに依存していないことを示す最小の利用例とする。第2の実用アプリや汎用フレームワークは作らない。

ノート一覧・複数ノート・検索・同期・設定画面・プラグイン・バックエンド切替・フォールバック・クラッシュ復旧・公開SDK・Electron API互換・自動更新は、このv0には含めない。Electronに対する性能上の優位性も、同一条件で直接比較するまでは判断しない。
