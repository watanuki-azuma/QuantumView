# QuantumView ロードマップ

最終目的は、ChromiumやOS標準WebViewに依存せず、HTML/CSS/JavaScriptのローカルUIをアプリへ組み込める、小さなWebView代替ホストを作ること。メモアプリは描画・日本語入力・ホスト連携を実証する最初のサンプルであり、プロジェクトの最終成果物ではない。

まず、日本語を入力し、自動保存し、再起動すると続きを書ける単一メモを完成させる。その実装で必要だったホスト処理だけを切り出し、メモ以外の最小画面でも利用できることを確かめる。この順序で進める。

## 現在地

- Servo 0.7.0とWebView2比較版のreleaseビルドと起動は成功。実行ファイルをSHA-256で固定し、各3回のアイドル測定を実施済み。
- Servoは表示・変換・取消・Ctrl+C/Vをユーザーが確認済み。IME確定後のフォーカス解除と、空の未確定文字更新を無視する問題を修正した。修正版で連続入力・取消・フォーカス移動・Backspaceの実機再確認を得た。文字数・クリア、項目100との往復、狭い幅での1列表示も確認済み。スクロールは移動量が十分だが段階的に動く、という操作感の課題が残る。
- Blitz/Dioxus Nativeは既存のHTML/JavaScriptを実行するWebViewの置き換えに合わないため、ユーザーの指示で候補と試作から除外した。過去の測定値は履歴として保持する。
- 画面取得ツールに障害がある。ツールの復旧や検証専用プロジェクトのビルドを、アプリ開発の前提にしない。

## 進める順番

| 段階 | やること | 終了条件 |
| --- | --- | --- |
| 1. 操作を確かめる | Servoで描画、日本語IME、編集、クリップボード、スクロール、リサイズを確認。WebView2を比較基準にする | 必須項目を合格・不合格・未確認で記録し、Servoでメモ用途が成立するか分かる |
| 2. 性能と継続可否を決める | 未測定の起動時間・スクロール時CPU/GPU/メモリを測る。条件が変わっていなければ既存のアイドル値は再利用 | 日本語操作を満たし、WebView2に対するリソース使用量と制約を説明してServoで進められるか判断する |
| 3. メモを完成させる | 採用構成だけに、単一メモの編集、自動保存、起動時の復元、保存状態・失敗の表示を追加 | 日本語・複数行・絵文字を編集し、終了直前の変更を含めて再起動後に復元できる |
| 4. 配布して使う | exeと必要なUI・リソースを一式にまとめ、ソースツリーの場所に依存せず起動できるようにする | 別フォルダーへ展開し、ビルドせず起動・編集・保存・再起動復元できる。ここをメモアプリv0の完了とする |
| 5. WebView代替ホストとして切り出す | メモで使った描画・入力・ホスト連携を、アプリ固有の状態・保存から分離する | 同じホストをメモと別の最小HTML/CSS/JavaScript画面から利用できる。APIは実際に使った操作だけに限定する |

Servoを実装候補として検証し、WebView代替としての要件を満たすかで継続可否を判断する。WebView2は比較基準であり、Chromiumへのフォールバックとして組み込まない。Servoに重大な未対応がある場合は、問題と必要な修正規模を整理して方針を見直す。

## 次の作業：段階2

1. 修正版Servoと比較用WebView2を使い、同じ画面・ウィンドウサイズ・入力手順でスクロール時のCPU・メモリ・GPUメモリを測る。アイドルの過去値は同じ版の値と混同しない。
2. コールド起動とウォーム起動を分け、内容が表示されるまでの時間を測る。画面録画を取得できない場合は未測定のまま明示する。
3. 基本操作の確認結果と、スクロールの滑らかさ・右クリックメニューなどの制約を添え、Servoを継続する判断材料をまとめる。

候補位置、全編集キー、複数行・絵文字の全ショートカット、トラックパッド、最小化復帰・DPIなどは引き続き未確認とする。既存の[操作確認手順](https://github.com/watanuki-azuma/QuantumView/blob/main/docs/comparison.md)を使い、同じチェックリストを別に作らない。確認のたびにコードを変えたり、計測をやり直したりしない。

## ビルドと測定の進め方

- ServoとWebView2の既存バイナリーと比較用HTML/CSS/JSは基準として保持する。比較画面を変更せず、メモ画面はServo側に追加する。
- 機能確認は既存バイナリーで始める。実機で確認した不具合の修正や、採用後の機能実装で必要になった場合だけビルドする。
- 関連する変更をまとめ、既存のCargoプロジェクト・target・ロックファイル・同じツールチェーンを使う。検証用の別Cargoプロジェクトや依存更新は追加しない。
- 修正版は別のリビジョンとして記録し、元の固定バイナリーや測定値へ混ぜない。再測定は変更の影響がある項目に絞る。
- 起動時間はウィンドウ生成時刻で代用せず、内容が描画されるまでを確認する。ウォーム起動とOS再起動後のコールド起動は分ける。
- ビルドと性能測定を同時に走らせず、待機中の同じ状態確認で対話を繰り返さない。

## メモアプリで必要になる設計だけを入れる

- 保存先はアプリ用のUTF-8ファイル1つ。自動保存では入力のたびの不要な書き込みを避け、終了時に未保存の変更を残さない。保存失敗を利用者が分かるようにする。
- メモの読込・保存に必要な最小のJS–Rust通信だけを実装する。複数エンジン共通の通信層は作らない。
- 配布用のリソース読込は、ソースツリーを離れて起動するために必要な範囲だけ変更する。
- 比較用UIを残すのは、同じ描画量で再測定できるようにするため。将来の画面遷移や複数画面対応のためではない。

段階5の別画面は、ホストがメモ固有のコードに依存していないことを示す最小の利用例とする。第2の実用アプリや汎用フレームワークは作らない。

ノート一覧・複数ノート・検索・同期・設定画面・プラグイン・バックエンド切替・フォールバック・クラッシュ復旧・公開SDK・Electron API互換・自動更新は、このv0には含めない。Electronに対する性能上の優位性も、同一条件で直接比較するまでは判断しない。
